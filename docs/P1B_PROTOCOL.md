# P1b protocol v1 — questions, map text, prompt, parser, scoring

Frozen before any planner number (task 008, claim-grade). A change is a dated entry at the bottom of this file and a
row in `DEVIATIONS.md`. Code: `spatialmem/p1b/`. Frozen artefacts: `configs/p1b_v1.yaml` (models, sampling,
sha256 of the question set).

## 1. Scenes and ground truth
- The 30 HSSD **eval** houses of `configs/hssd_scenes.yaml`. GT = `data/hssd_runs/all/<scene>/gt.json` via
  `spatialmem.hssd.gt.load_hssd_gt` (canonical labels, CONTRACT 2026-10-27e). Up axis as exported (1 = y).
- Objects with a STRUCTURAL label (`wall`, `floor`, `ceiling`, `undefined`) are removed, together with every relation
  that touches one. What remains is "the GT map" of the house: objects (id, label, AABB) and relations (subj, pred, obj).
- `next_to` is unordered: A next_to B holds if either direction is exported.

## 2. Question types (templated from the GT map)
Labels appear in question text with `_` replaced by a space. `n(L)` = number of objects with label L in the house.

| type | template | candidates | answer |
|---|---|---|---|
| existence (pos) | `Is there a/an <L> in the house?` | every L with n(L) ≥ 1 | `yes` |
| existence (neg) | same | every L in the eval-30 label vocabulary (union over the 30 GT maps) with n(L) = 0 | `no` |
| relation | `What is the <A> on?` / `What is the <A> in?` / `What is the <A> next to?` | label A with n(A) = 1; object a; predicate p; the set of labels of all b with (a p b) has exactly one element B, B ≠ A | label B |
| counting | `How many <plural(L)> are there in the house?` | every L with 1 ≤ n(L) ≤ 6 | n(L) |
| find | `Which object is the <A> that is on / in / next to the <B>?` (`on the`, `in the`, `next to the`) | labels A, B with n(A) ≥ 2, A ≠ B, predicate p, and exactly one object a of label A with (a p b) for some b of label B | id of a; scored by centre distance (§5) |

- `a/an`: `an` if the spoken label starts with a vowel letter.
- `plural(L)` on the spoken label: ends in `ss`, `x`, `z`, `ch`, `sh` → `+es`; else ends in `s` → unchanged; else ends in
  consonant + `y` → `y`→`ies`; else `+s`.
- **Sampling, seed 114.** Per house and type, candidates are sorted (by the tuple shown in the generator) and drawn with
  `random.Random(f"114:{scene}:{type}")`, without replacement:
  - existence: 2 positive + 2 negative;
  - relation: 4, round-robin over predicates `on`, `in`, `next_to` (skip an empty predicate), one candidate per (A, p) pair;
  - counting: 4;
  - find: 4, round-robin over predicates as for relation, one candidate per (A, p, B) triple.
  If a house has fewer candidates than the quota, all of them are taken; no backfill.
- Question id `"<scene>:<type>:<k>"`. Frozen file: `data/p1b/questions_v1.jsonl` (git-ignored: derived from HSSD),
  regenerated byte-identically by `uv run python -m spatialmem.p1b.questions`; its sha256 is committed in
  `configs/p1b_v1.yaml` before any planner number.

## 3. Map as text (one serialiser for GT maps, degraded maps and real mapper outputs)
**v1.2 (2026-10-29, the one pre-registered prompt fix after G4 failed on v1.1; v1 / v1.1 in the change log).**
```
HOUSE <scene> (metres, y up)
OBJECTS: [id,label,[cx,cy,cz]]
[<id>,"<label>",[cx,cy,cz]]
...
RELATIONS on: [subject id,subject label,object id,object label]
[<s>,"<label of s>",<o>,"<label of o>"]
...
RELATIONS in: [subject id,subject label,object id,object label]
...
RELATIONS next_to: [subject id,subject label,object id,object label]
...
```
- One JSON array per line, no spaces. Ids are the map's integer ids; labels with `_` kept as in the vocabulary.
- Numbers rounded to 1 decimal (`f"{v:.1f}"`, `-0.0` → `0.0`). No sizes (no question type reads them).
- Objects sorted by id (numeric). The three RELATIONS sections always appear, in the order on, in, next_to (a section
  may be empty); lines inside a section sorted by (subject id, object id); `next_to` as exported (one line per pair).
- The parser inverts it exactly (G3): `parse(serialise(m))` gives the same ids, labels and relations and centres equal to
  the rounded values (sizes are not carried); `serialise(parse(t)) == t` byte for byte; the labels on a relation line
  must equal the labels of those ids in OBJECTS.

## 4. Prompts (temperature 0, fixed; `spatialmem/p1b/prompt.py`)
**Map rows** (GT map; later degraded and real maps):
- system: `You answer questions about one house using only the map of the house given below. Reply with the answer only, in the requested format, with no explanation.`
- user: `<map text>\n\nQuestion: <question>\nAnswer format: <format>`

**Images-only row:** the user message carries 8 RGB frames of the house's stream, frame indices
`round(linspace(0, N-1, 8))` (N = frames in `rgb/`), then the text:
- system: `You answer questions about one house using only the photos of the house given above. Reply with the answer only, in the requested format, with no explanation.`
- user text: `Question: <question>\nAnswer format: <format>`
- find questions are not asked in this row: scored wrong ("not answerable without a map").

| type | `<format>`, map rows | `<format>`, images-only row |
|---|---|---|
| existence | `yes or no` | `yes or no` |
| relation | `one object label, exactly as written in the map` | `one label from this list: <eval-30 vocabulary, sorted, comma-separated, spoken form>` |
| counting | `a single integer` | `a single integer` |
| find | `one object id (the number), exactly as written in the map` | — |

## 5. Parser and scoring (`spatialmem/p1b/parse.py`; fixed, no per-model change)
The raw output `r` is lowercased; `_` and `-` become spaces; whitespace is collapsed.
- existence: first match of `\b(yes|no)\b` → that word; none → invalid.
- counting: the earliest of a `\b\d+\b` match or a number word `zero` … `twenty` (whole word) → that integer; none → invalid.
- relation: candidates = labels present in the given map (map rows) or the vocabulary list (images row), in spoken form;
  the candidate whose whole-phrase match (`\b…\b`) starts earliest in `r` wins, ties → the longer candidate; none → invalid.
- find (v1.1): first match of `obj (\d+)` in the normalised text (`obj_12`, `obj 12`), else the first `\b\d+\b` → id;
  the id must exist in the given map; correct iff the 3D distance between that object's centre (map) and the GT answer object's AABB centre ≤ 1.0 m.
- existence / relation / counting are correct iff the parsed value equals the answer key. Invalid = wrong.
- Accuracy = correct / questions, per type and overall (micro over all questions of the row).

## Change log
- 2026-10-29: v1 written (task 008), before any planner number.
- 2026-10-29 (v1.1, before any planner number): §3 map text v1 (one JSON object per line, keys id / label /
  center / size, ids `obj_<n>`, 2 decimals) → compact JSON arrays, integer ids, 1 decimal. Why: v1 gt7b prompts measured
  under the Qwen2.5-VL-7B chat template were min 8,736 / median 19,007 / max 51,951 tokens; 48 of 479 exceed the model's
  native 32,768 context (YaRN beyond it is not recommended by the model card and would change every prompt). v1.1 map
  text: max 31,303 tokens (house 102816600, 493 objects, 1,287 relations), median 10,943; 2 decimals would be 34,261.
  No question type uses geometry finer than 1 m (find is scored at 1.0 m). Find format and parser follow the integer
  ids (`obj_` prefix still accepted). Questions, answer keys and their sha256 are unchanged.
- 2026-10-29 (v1.2) — **the one diagnosed prompt fix allowed by §7, committed before any v1.2 number.**
  Diagnosis of `gt7b` on v1.1 (overall 49.5 % < 70 %; existence 100.0, counting 66.7, relation 14.3, find 16.7; parser
  invalid 3 of 479, so not a parser failure): relation and find need a two-hop id join (subject id on an object line →
  relation line → object id → its label). The 7B model fails the join even on short maps (< 10k tokens: relation 23 %,
  find 27 %); 49 of 102 wrong relation answers repeat the question's own subject label; 44 of 100 wrong find answers
  are an object of the right label A but not the one with the relation. Fix: relation lines carry both labels (the join
  becomes one line). To stay inside the 32,768 native context, sizes are dropped (no question reads them) and relations are
  grouped by predicate (saves the predicate on every line): GT max 29,034 tokens (v1.1 31,381; full denormalised lines
  with sizes 38,672). Questions, answer keys, parser, scorer, gates and kill rules unchanged.
  Verdicts after the fix: **G4 is read on `gt7b` with v1.2 prompts**; the §7 escalation reads `gt72b` with v1.2 prompts.
  The v1.1 `gt7b` / `img7b` / `gt72b` runs are reported as pre-fix rows (diagnosis), never as the gate number.
  (`img7b` has no map text; its v1.1 prompts are unchanged and stay the images-only row.)
